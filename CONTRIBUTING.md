# Contributing

Thank you for improving this project.

## Before You Start

- Open an issue before a substantial architecture or behavior change.
- Keep each pull request focused on one outcome.
- Never include secrets, personal data, production exports, or sensitive infrastructure details.
- Report security findings through [SECURITY.md](SECURITY.md), not a public issue.

## Pull Requests

A complete pull request should include:

1. the problem and intended outcome;
2. the tested environment;
3. exact validation steps and results;
4. documentation for operational changes;
5. security, migration, and rollback considerations;
6. any assumptions that still require field validation.

Use clear commit messages and update examples when interfaces or configuration change.
